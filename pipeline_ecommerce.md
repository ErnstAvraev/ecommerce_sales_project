# Декомпозированный аналитический пайплайн: ecommerce_sales_analytics_5000.csv

---

**Цель анализа**: Определить оптимальный коридор размеров скидок для максимизации выручки на заказ без чрезмерной каннибализации маржинальности, а также выявить категории товаров, нечувствительные к скидкам.
**Аналитические вопросы**: Как изменяются `quantity` и `revenue` при переходе между интервалами скидок? Наблюдается ли статистически значимый квадратичный эффект замедления/падения выручки после порога 20-25%? Есть ли нечувствительные категории (`product_category`)?
**Ожидаемый результат**: Сводные таблицы, визуализации с полиномиальной регрессией, отчёт о статистической значимости и практические рекомендации.
**Источники данных**: Файл `ecommerce_sales_analytics_5000.csv` (Kaggle: abbas829/ecommerce-sales-dataset). Период данных требует проверки. Уровень доверия: средний (требуется валидация бизнес-логики расчёта выручки).

## 📥 INPUT DATA (Входные данные и контекст)

### Этап 1: Загрузка и первичная инспекция
1. **Загрузка данных**: Импорт данных в аналитическую среду с явным указанием кодировки и разделителя.
2. **Проверка размерности данных**: Контроль количества строк (ожидается ~5000) и столбцов (ожидается 12: `order_id`, `order_date`, `customer_id`, `product_category`, `region`, `quantity`, `unit_price`, `discount`, `payment_method`, `delivery_days`, `customer_rating`, `revenue`).
3. **Первичный просмотр данных**: Визуальная проверка первых и последних строк для оценки корректности парсинга и отсутствия очевидных аномалий.
4. **Изучение типов данных**: Проверка типов: `order_date` (требует преобразования в datetime), `discount` (float), `quantity` (int/float), `revenue` (float).

### Этап 2: Валидация целостности данных
1. **Проверка названий столбцов**: Приведение названий к единому стилю (snake_case), удаление скрытых пробелов.
2. **Проверка пропусков**: Анализ доли отсутствующих значений. Критические поля: `discount`, `quantity`, `unit_price`, `revenue`.
3. **Обработка пропусков**: Строки с пропусками в ключевых метриках (`quantity`, `revenue`) удаляются. Пропуски в `discount` интерпретируются как отсутствие скидки (заполнение 0.0), если это подтверждается бизнес-логикой.
4. **Проверка дубликатов**: Проверка на полные дубликаты строк. *Допущение*: Если `order_id` повторяется, необходимо выяснить, является ли строка уровнем заказа или уровнем товарной позиции. Агрегация должна проводиться на уровне `order_id` или `product_category`.

## ⚙️ DATA TRANSFORM (Преобразование и подготовка данных)

### Этап 3: Бизнес-валидация и очистка
1. **Проверка числовых столбцов**: Анализ базовой статистики для `quantity`, `unit_price`, `discount`, `revenue`. *Контроль*: `quantity` > 0, `discount` ∈ [0.0, 1.0], `revenue` >= 0.
2. **Проверка категориальных столбцов**: Проверка уникальных значений и частотного распределения для `product_category`, `region`, `payment_method`. Стандартизация регистра.
3. **Проверка дат**: Преобразование `order_date` в формат даты. Проверка минимальной и максимальной даты для выявления выбросов (дат из будущего или прошлого).
4. **Создание производных признаков**: 
   - `discount_pct`: размер скидки в процентах (`discount` * 100).
   - `discount_bin`: интервал скидки ('0%', '1-10%', '11-20%', '21-30%', '>30%').
   - *Открытый вопрос / Валидация*: Необходимо проверить формулу: `revenue` == `quantity` * `unit_price` * (1 - `discount`). Если `revenue` рассчитана без учёта скидки, метрику необходимо пересчитать.

### Этап 4: Разведочный анализ и агрегация
1. **Первичный разведочный анализ (EDA)**: Распределение заказов по интервалам `discount_bin`. Гистограммы распределения `quantity` и `revenue` для оценки наличия тяжёлых хвостов.
2. **Построение агрегированных таблиц**: Группировка по `discount_bin` и `product_category` с расчётом среднего `quantity`, среднего `revenue` и количества заказов (для оценки статистической мощности).
3. **Проверка выбросов и аномалий**: Анализ точек, сильно отклоняющихся от тренда. *Стратегия*: Оценка природы выбросов (оптовые заказы, ошибки ввода). При необходимости применение робастных методов или удаление экстремальных квантилей (например, топ 1% по `quantity`).
4. **Проверка связей между признаками**: Построение матрицы корреляций (Пирсона или Спирмена) для числовых признаков (`discount`, `quantity`, `unit_price`, `revenue`, `delivery_days`, `customer_rating`).

### Этап 5: Моделирование и верификация
1. **Выполнение основного расчёта по задаче**: Построение модели полиномиальной регрессии второй степени: `revenue` ~ `discount_pct` + `discount_pct`². Проверка статистической значимости (p-value) коэффициентов. Расчёт вершины параболы (оптимальная скидка) по формуле: `-b / (2 * a)`. Повторение процедуры для `quantity` и сегментный анализ по `product_category`.
2. **Проверка корректности расчётов**: Контрольная сверка сумм `revenue`. Проверка того, что рассчитанная вершина параболы находится в пределах 0–100%. Проверка знака коэффициента `a` (должен быть отрицательным для подтверждения гипотезы).
3. **Интерпретация результатов**: Формулировка выводов на основе фактов: указание конкретного процентного порога скидки, после которого наблюдается падение средней выручки, и выявление нечувствительных категорий.
4. **Ограничения анализа**: 
   - Отсутствие данных о себестоимости (анализ максимизирует выручку, а не прибыль).
   - Наблюдательный характер данных (корреляция не доказывает причинно-следственную связь).
   - Отсутствие контроля внешних факторов (сезонность, действия конкурентов).

## 📤 OUTPUT DATA (Результаты, выводы и артефакты)

### Этап 6: Визуализация и бизнес-решения
1. **Построение визуализаций**: 
   - Scatter plot: `discount_pct` (X) vs `revenue` (Y) с линией тренда полиномиальной регрессии второй степени.
   - Scatter plot: `discount_pct` (X) vs `quantity` (Y) с линией тренда.
   - Столбчатые диаграммы средних значений `revenue` и `quantity` по `discount_bin` в разрезе `product_category`.
2. **Подготовка рекомендаций**: Установить системный лимит скидки на уровне выявленного оптимального порога. Провести аудит промо-активностей для нечувствительных категорий. Инициировать A/B-тестирование для валидации причинного эффекта.
3. **Подготовка итогового отчёта**: Формирование документа, содержащего цель, описание данных, ключевые метрики, визуализации, интерпретацию, ограничения и рекомендации.

### Этап 7: Контроль качества и сдача
1. **Сохранение результатов**: Экспорт очищенного датасета с новыми признаками (`discount_pct`, `discount_bin`), сводных таблиц агрегации и визуализаций в назначенные директории в форматах CSV и PNG/PDF.
2. **Проверка воспроизводимости**: Фиксация версий используемых библиотек, обеспечение линейного выполнения скриптов обработки без ручных вмешательств, наличие комментариев, поясняющих логику преобразований.
3. **Финальный QA анализа**: Чек-лист проверки: цель сформулирована, единица анализа определена, бизнес-формула проверена, пропуски/дубликаты обработаны, выбросы проанализированы, статистическая значимость проверена, ограничения указаны, рекомендации следуют из расчётов.
